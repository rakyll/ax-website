Why AX

Agents are a new kind of workload.

They are neither stateless microservices nor run-to-completion batch jobs. They accumulate state, need strict isolation, call out to model APIs and tool servers, and can burn money in a loop if nobody is watching. AX gives you four small primitives that handle all of that declaratively.

Task

Isolated execution

Run untrusted agent code in a sandbox with CPU and memory limits. Cheap to create, suspend, and throw away.

 Workspace

Start warm

Pre-wire Git repos, MCP servers, and skill packages so every agent starts with its environment ready.

 Gateway

Fenced network

Lock outbound traffic down to an explicit allowlist of hosts and ports, such as your LLM provider and Git host.

 Model

One place for credentials

Configure which LLM the platform uses, with the API key pulled from a Kubernetes secret. Rotate it with one apply.
ax suspend ax resume

Pause an idle agent and pick up exactly where it left off. The workspace volume is snapshotted and restored.

ax ssh

Shell into a running agent to see what it is doing. Look over its shoulder without leaving your terminal.

ax watch

Stream phase and condition transitions live, from WorkspaceReady through Ready.

How it works

Built for billions of tasks, not thousands.

Storing millions of short-lived tasks as Kubernetes CRDs pushes etcd past its comfort zone. AX keeps its state in Redis and uses Redis Streams as the work queue between the API server and a horizontally scaled pool of controllers.

  1. ax applyValidate and submit manifests over gRPC
  2. ax-serverPersist to Redis and publish an event
  3. ax-controllerConsume the stream and reconcile toward desired state
  4. Agent SubstrateProvision the sandbox, assign a worker, apply egress policy
